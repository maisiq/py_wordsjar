# Smoke-тесты бэкенда

Минимальный набор проверок «бэкенд вообще работает»: приложение поднимается
реальной фабрикой `main.init()`, все роуты на месте, health/readiness-пробы
отвечают, закрытые эндпоинты не пускают анонимов, ошибки возвращаются в
стабильной обёртке `{detail, code, request_id}`, а полный пользовательский
сценарий проходит от регистрации до логаута.

## Два уровня

| Файл | Что проверяет | Внешние зависимости |
|------|---------------|---------------------|
| `test_smoke.py` | HTTP-слой: старт приложения, состав роутов, `/healthz`, `/readyz` (503 без БД), OpenAPI, 401 для анонимов на закрытых эндпоинтах, 404/422-конверты, валидация сортировки и курсоров | не нужны |
| `test_smoke_db.py` | Полный сценарий против настоящего PostgreSQL: signup → login → словарь → поиск → банка → экзамен → refresh → logout, плюс админское добавление слов и `/readyz` = 200 | PostgreSQL |

## Запуск

```bash
cd backend

# только HTTP-слой (БД не нужна)
uv run pytest

# всё вместе: укажите отдельную одноразовую базу
export WORDSJAR_TEST_DB_DSN=postgresql+psycopg://postgres:postgres@localhost:5432/wordsjar_test
uv run pytest -v
```

> ⚠️ `WORDSJAR_TEST_DB_DSN` должна указывать на **выделенную тестовую базу**:
> набор прогоняет на ней `alembic upgrade head` и пишет в неё тестовые данные.
> Если переменная задана, но база недоступна, тесты упадут (а не промолчат),
> чтобы не прятать поломку в CI.

## Как это устроено

- `conftest.py` кладёт `backend/app` в `sys.path` (приложение использует
  плоские импорты) и задаёт тестовые переменные окружения
  (`WORDSJAR_BACKEND_DB_DSN`, `WORDSJAR_BACKEND_JWT_KEY`, docs) **до** импорта
  приложения; `main.init()` вызывается один раз на сессию.
- HTTP-слой работает через `fastapi.testclient.TestClient` (in-process ASGI,
  lifespan включён — это заодно проверка чистого старта и останова). Без
  `WORDSJAR_TEST_DB_DSN` приложение конфигурируется заведомо недоступным DSN
  на домене `.invalid`, поэтому «база лежит» — детерминированное состояние.
- Перед каждым тестом сбрасываются in-process rate-limiter'ы: иначе лимит
  регистраций (5 в час на клиента) был бы общим на всю сессию.
- Данные в БД-тестах уникальны (uuid в именах пользователей и слов), поэтому
  повторные запуски по одной и той же базе не мешают друг другу.
- Миграции alembic выполняются в подпроцессе: `env.py` переконфигурирует
  логирование через `fileConfig` и иначе «погасил» бы логгер приложения до
  конца pytest-сессии.

## CI

Workflow `.github/workflows/backend-smoke.yml` поднимает сервис PostgreSQL,
выставляет `WORDSJAR_TEST_DB_DSN` и прогоняет оба уровня на каждый push в
`main` и на каждый pull request.
